# Platform 1 · 研究演化证据工具 v0.1 Final PRD

Oct 10, 2026 · @Celeste

**怎么读这份文档：** 第 1–6 节写给你，全部用白话，读完就知道要做什么、为什么做、做到什么程度。第 7–18 节写给 Claude Code，是技术规格；每一节开头有一句「白话」，你只看这一句就够了。这是 v0.1 的最终版，取代 10 月 10 日的第一版 PRD。

## 1. 这是什么，为什么做

**一句话：** 这是一个装在你自己电脑上的研究记录工具。它把研究过程中的各种东西记成互相连接的记录，并给每条记录留下签名和时间证明，让「这个研究是怎么一步步变成现在这样的」看得见、查得到。

**为什么做：**

- 研究最后通常只剩一篇论文或一个最终文件。中间的想法、失败的实验、改过的模型散在各处，别人看不到，时间长了你自己也说不清。
- 你自己写的日期，别人没法相信，因为能改。
- 直接把文件交给 AI，AI 只能猜当时发生了什么，它不知道日期是真是假。
- 这个工具在事情发生的时候就把记录固定下来。以后谁都改不了，包括你自己。

**给谁用：** 先给你自己，用来记录 FSF。然后是研究做得久、材料散在很多地方、以后要向导师、评审或合作者解释研究过程的人：研究生、学生研究者、独立研究者。

**它不是什么：**

- 不是 GitHub 的替代品。GitHub 是证据的来源之一。
- 不是「原创证明」。以后如果发生时间或贡献上的争议，这些记录可以作为证据的一部分，但这只是附带的用处，不是主要承诺。

## 2. 它能证明什么，不能证明什么

**能证明：**

- 这条记录最晚在某个时间已经存在。「这条记录」指的是全部内容：文件、类型、和其他记录的关系、你写的说明。
- 之后没有被改过。
- 记录的先后顺序。
- 所有记录都是用同一把签名钥匙签的。

**不能证明：**

- 是你本人想出来的。签名钥匙只代表「同一把钥匙」，不代表某一个人。
- 你是第一个想到的。
- 你为什么这样改。
- 内容是对的，或者有价值。

### 三种信息，永远分开显示

| 种类 | 意思 | 例子 |
| --- | --- | --- |
| 可验证记录 | 有签名和时间证明，任何人都能自己检查 | 这个实验文件最晚在 5 月 3 日已经存在 |
| 作者陈述 | 你自己说的。系统只能证明「你在那天这样说过」，不能证明说的是真的 | 「因为实验失败，所以改了假设」；「这份笔记是去年写的」 |
| AI 推断 | AI 根据记录做出的判断。第二版才有 | 「第 3 版比第 1 版多了两个概念」 |

「可验证记录」只说明这条记录当时已经存在、之后没有被改过，不说明里面说的话是真的。

### 两种时间证明，名字不同，意思也不同

| 名字 | 多久拿到 | 要相信谁 |
| --- | --- | --- |
| 第三方签名时间证明 | 几秒 | 要相信发证明的机构没有说谎；它的签名本身任何人都能检查 |
| 比特币时间锚定 | 先显示「等待中」，通常几个小时后变成「已确认」，时间不保证 | 不用相信任何机构；任何人都能对照公开的比特币记录自己检查 |

每条记录旁边会分开显示这两项，例如：「第三方签名时间证明：已验证；比特币时间锚定：等待中」。几个小时后，第二项变成「已确认」。

### 最重要的一条规则：只能追加，不能修改

已经留下证明的记录，任何人都不能改，包括你自己。后来想补一个关系、标一个里程碑、补一句说明、更正一个错误，都只能新加一条记录，它有自己的签名和时间证明。界面上会显示「这个关系是 10 月 11 日补加的」。

这样一来，别人不但不能伪造文件，也不能事后重新连线，改写整张演化图。

## 3. 第一版用起来是什么样

用 FSF 举例，从头走一遍。最后你看到的不是一个文件夹，也不是一串代码提交，而是下面这样一张图。

（示意图：FSF 示例，7 条记录、6 种类型、3 种关系。图见在线文档第 3 节。）

每个框是一条记录，都有自己的签名和两种时间证明。虚线框里的是作者陈述，单独标出，不当作已验证的事实。

1. **第一次打开。** 程序生成你的签名钥匙，并提醒你备份。钥匙丢了，以后的新记录就是另一个身份。
2. **新建研究项目。** 比如叫「FSF」。
3. **记一条记录。** 先选类型，共 9 种：想法、笔记、论断/假设、文档、代码、实验、数据、图、发表。再写内容或拖入文件。代码可以只填仓库地址和提交编号，但这只是一个外部引用：仓库以后删了，就拿不回那份代码。想真正保留代码内容，就同时附上代码打包文件；发表的论文填 DOI。
4. **说明它和之前哪条有关。** 关系只有 3 种：修改自、派生自、用到了。可以写一句「为什么」，它会显示为作者陈述。重要的记录可以标成里程碑。
5. **点「记录」。** 几秒内显示「第三方签名时间证明：已验证」；几个小时后显示「比特币时间锚定：已确认」。你的内容没有离开电脑，发出去的只是一串根据内容算出来的号码。
6. **放进旧材料。** 以前的笔记也能记，但只能证明「记进来的那天已经存在」。你填的更早日期显示为作者陈述；有 DOI 之类外部证明的，显示为第三方参考。
7. **看演化图。** 所有记录按时间从左到右排开，按类型分行，箭头表示关系。可以切换成「只看里程碑」，几百条记录缩成关键几步。点任何一条，可以看原文件、两种时间证明、前后的记录、改了什么、作者说明，以及后来补加的关系或更正。
8. **发给别人。** 导出一个压缩包，里面有一份网页报告和一个检查程序。对方不用装这个工具，也不用相信你或我们，自己就能检查。每一条可以选公开多少：全部公开；只公开结构（看得到标题和关系，看不到内容）；只证明存在。

## 4. 第一版不做什么，以后做什么

第一版只做一件事：把记录做可靠。其他都往后放。

| 第一版不做 | 原因 |
| --- | --- |
| 账号、云同步 | 一个人在自己电脑上用，不需要；原文不上传，本身就是这个工具的好处 |
| AI 分析 | 先证明「没有 AI，这张图本身就有用」；而且 AI 要把内容发给 AI 公司，得先想好怎么征求你的同意 |
| 自动连接 GitHub、读取全部历史 | 4 天做不完；而且过去的提交日期可以改，导入进来也只能算作者陈述 |
| 论断检查、原创判断、贡献分析、人才匹配 | 属于以后的平台 |
| 网页版、手机版 | 先在 Mac 上做好 |

**第二版的 AI，规则现在先定好：**

1. 只根据记录回答，不凭空说。
2. 每句重要的话都指向具体的记录，比如「第 17 条记录，5 月 3 日」。
3. 一律标成「AI 推断」，和可验证记录、作者陈述分开。
4. 把任何内容发给 AI 之前，先问你同不同意；或者改用在你电脑上运行的 AI。
5. AI 的判断如果要保存，也作为新的一条记录追加，标明来源是 AI。

**更以后：** 自动记录（连接 GitHub、笔记软件，一有修改就记下来）、贡献分析、论文审计。它们都建立在这一版留下的记录上。

## 5. 和现有工具比

每个现有工具都只做了一部分，但「有没有人需要我们补上的那部分」还没有被证明。

| 现有工具 | 它擅长 | 它做不到 |
| --- | --- | --- |
| GitHub | 代码文件的版本 | 只管代码；提交日期由自己电脑写，可以改；不管笔记、实验、论文之间的关系 |
| 直接问 AI | 读懂材料、写总结 | 不知道日期是真是假，只能猜当时发生了什么 |
| [OSF](https://help.osf.io/article/759-details-of-osf-projects-transition) | 冻结的研究记录（注册、预注册），可以反复建 | 2026 年 11 月 16 日起不能新建项目，2027 年 2 月 19 日起现有项目变成只读；以后不再提供持续更新的项目空间 |
| [ResearchEquals](https://researchequals.com/en-US) | 公开发布各种研究成果，每个版本可以有 DOI | 发布就是公开；核心不是把不同类型的东西连成一张演化图；规模小，自己写明 2027 年后的运营还需要资金 |

**我们的不同：** 不用公开；记录连同关系一起被固定；不同类型的东西连在一张图里；事实和解释分开显示。

**「原创」放在哪里：** 它降级成附带的用处。如果以后发生时间或贡献上的争议，这些记录可以作为证据的一部分，但我们不以此为卖点。

## 6. 怎么判断做对了没有，什么时候做

第一版要回答的不是「技术能不能做出来」，这些技术都做得出来。要回答的是：**人有没有必要特意记录自己的研究过程。**

**两个检验：**

1. **FSF 检验。** 你用它整理 FSF 之后，只看这张图、不用 AI，是不是比「GitHub + 文件夹 + 直接问 AI」明显清楚？
2. **同学试用。** 请 3 到 5 个正在做研究的同学用一周，问他们：「如果你在做一个持续几个月的研究，你愿不愿意在几个关键节点顺手留下这条记录？为什么？」更要看他们实际有没有记，而不是只听他们说「这个想法挺好」。

**结果怎么用：**

| 结果 | 下一步 |
| --- | --- |
| 两个都通过 | 做第二版，加 AI 分析 |
| FSF 通过，同学不用 | 先当你自己的工具和以后平台的基础，暂时不当独立产品 |
| 两个都不通过 | 停下来，改成别的工具里的一个功能 |

（示意图：建议日程 10/10 至 11/1。图见在线文档第 6 节。）

## 7. 不可违反的规则

**白话：** 这几条比后面任何技术细节都优先；冲突时以这里为准。

1. **Append-only（只追加）。** 已签名并已提交时间证明的记录，任何字段都不能修改或删除，包括关系、里程碑状态、作者陈述。补充、更正、撤回一律作为新记录追加，各自有签名和时间证明。数据库在 `records` 表上用 SQLite 触发器拒绝 `UPDATE` 和 `DELETE`；接口层不提供编辑已有记录的端点。界面显示的「当前状态」由按 `seq` 顺序重放全部记录得出。
2. **三种信息来源永不混用。** 每个展示出来的信息都带来源标签：`verified`、`author`、`ai`（v0.1 不产生）。`author` 和 `ai` 的内容永远不能显示成已验证事实。
3. **本地优先。** 原文、附件、标题、说明都不离开本机；对外只发送时间证明协议所需的哈希承诺和协议数据（例如记录 ID，或由它再加随机数算出的哈希）；原文、标题、说明、附件永不发送。网络请求本身仍会让对方看到 IP 地址和请求时间。没有账号，没有云同步。时间证明需要联网，这是唯一的出站流量。
4. **两种时间证明分开。** 第三方签名时间证明（RFC 3161）与比特币时间锚定（OpenTimestamps）在界面、报告、代码、验证结果里都分开命名、分开显示状态，不能合并成一个笼统的「已验证时间」。
5. **宣称边界。** 界面、报告、README 里不出现「原创证明」「认证」「确权」「保护你的想法」。能说的只有：最迟在某时已存在、之后未被修改、先后顺序、由同一签名钥匙签署。
6. **范围。** 第 4 节「第一版不做」的内容一行都不写，看起来顺手也不加。
7. **冲突处理。** PRD 与实际情况冲突时（例如某个库的接口不同），选最接近 PRD 意图的做法，并记进 `docs/DECISIONS.md`，不要悄悄偏离。

## 8. 数据模型

**白话：** 系统里只有一种东西，叫「记录」。研究成果、后来补的关系、里程碑、补充说明、撤回，都是不同种类的记录，按顺序排成一条链，每条都签名、都留时间证明。

### 记录种类

| `kind` | 用途 | 载荷里的关键字段 |
| --- | --- | --- |
| `genesis` | 第一次启动 | `author_label`（自我声明）、`public_key`（Ed25519 公钥） |
| `entry` | 一件研究成果 | `project`、`node_type`、`title`、`content` 或 `external`、`relations`、`author_statement`、`milestone`、`import` |
| `link` | 后来补加或撤回一个关系 | `from`、`to`、`rel`、`op`（add / withdraw）、可选 `statement` |
| `milestone` | 后来标记或取消里程碑 | `target`、`op`（set / unset） |
| `statement` | 后来补充说明或更正 | `target`、`source`（v0.1 只有 `author`）、`text`、可选 `corrects` |
| `retraction` | 撤回一件成果 | `target`、`reason` |

规则：`target`、`from`、`to` 必须指向本安装里 `seq` 更小的记录；`link` 的两端必须是 `entry`。

### 节点类型：`entry.node_type`，9 种

`idea` 想法 · `note` 笔记 · `claim` 论断/假设 · `document` 文档 · `code` 代码 · `experiment` 实验 · `dataset` 数据 · `figure` 图 · `publication` 发表

### 关系：`rel`，3 种

`revises` 修改自 · `derived_from` 派生自 · `uses` 用到了。方向统一为「新记录 rel 旧记录」，例如「修改后模型 revises 第一版公式」。格式允许以后新增种类；验证器遇到不认识的 `rel` 照常验证，界面显示为「其他关系」。

### 外部引用：`entry.external`

- 代码：`{"repo_url": "…", "commit": "<提交哈希>"}`，可选附 `git archive` 打包文件。只有提交哈希时，只能证明「当时记录了这个代码引用」，仓库删除或改写后可能无法再取回或核对代码；附上打包文件，才真正保留了代码内容，界面在只填提交哈希时要提示这一点；git 自己记录的提交日期只算作者陈述。
- 发表：`{"doi": "…"}` 或 `{"url": "…"}`，证据等级为 L2（第三方参考）。

### 清单与载荷

每条记录由很小的清单（manifest）和载荷（payload）组成，各自用 RFC 8785（JCS）规范化成字节。记录 ID = SHA-256（清单字节）；清单里写着载荷的 SHA-256。隐去一条记录时可以只公开清单：日志链照样能验证，内容不泄露。

```jsonc
// 清单：记录 ID = SHA-256(JCS(清单))
{ "schema": "rprov.record/1", "kind": "entry", "installation": "<uuid>",
  "seq": 17, "prev": "<上一条记录 ID；genesis 为 null>", "payload_sha256": "<SHA-256(JCS(载荷))>" }

// entry 的载荷
{
  "nonce": "<32 字节随机数，hex>",
  "local_time": "2026-10-12T14:03:05Z",
  "project": { "id": "<uuid>", "title": "FSF" },
  "node_type": "experiment",
  "title": "数值实验 1",
  "content": { "body": { "sha256": "…", "size": 1234, "media_type": "text/markdown" },
               "files": [ { "name": "run1.csv", "sha256": "…", "size": 88210, "media_type": "text/csv" } ] },
  "external": null,
  "relations": [ { "to": "<记录 ID>", "rel": "uses" } ],
  "author_statement": "<可选：为什么>",
  "milestone": false,
  "import": null,
  "ext": {}
}
```

导入旧材料时 `import` = `{"claimed_date": "2025-11", "precision": "month", "level": "L1" 或 "L2", "references": [ … ]}`。`ext` 写入时为空对象，验证器接受并忽略其内容。清单和载荷里禁止浮点数。

### 信息来源对照

| 展示的信息 | 来源标签 |
| --- | --- |
| 内容哈希、存在时间、先后顺序、签名 | `verified` |
| 关系、里程碑、作者说明、导入的声称日期 | `author`（但「作者在 T 时这样声明」本身是 `verified`） |
| AI 的判断（v0.2） | `ai`：作为 `statement` 记录追加，`source: "ai"`，并列出 `based_on` 的记录 ID |

### 本地数据库

- `records`（只追加，触发器保护）：`id`、`kind`、`seq`（唯一）、`prev_id`、`manifest_bytes`、`payload_bytes`、`signature`、`project_id`、`created_local`。两份字节原样保存，验证时绝不重新序列化。
- `anchors`：`record_id`、`provider`（`tsa` / `btc`）、`status`（pending / confirmed / failed）、`proof_bytes`、`verified_time_utc`、`detail`、`attempts`、`last_error`。时间证明不是记录，状态可以更新。
- `blobs`、`record_files`：内容按哈希存放在 `data/blobs/ab/cd/<sha256>`。
- `projects`：本地显示用，可改名；被固定的是每条 `entry` 载荷里当时的项目名。
- 图的缓存表可以随时从 `records` 重建。

## 9. 哈希、签名与两种时间证明

**白话：** 每条记录先算出一串号码，用你的钥匙签名，再把号码拿去两个地方留时间证明。内容本身不发出去。

### 哈希

- 全部使用 SHA-256；清单和载荷用 RFC 8785（JCS）规范化，可用 Trail of Bits 的 `rfc8785` 包（先确认仍在维护）或自己实现并用测试向量校验。
- 每份载荷含 32 字节随机数（`secrets.token_bytes(32)`）。别人拿到记录 ID 也无法靠猜内容来对号码。
- 正文写入前统一为 UTF-8、换行统一为 LF；哈希的、存的、导出的都是这同一份字节。
- 内容哈希不加盐，验证者可直接用 `sha256sum` 核对。代价是别人已知或能猜到的内容可能被对照确认，所以「只证明存在」模式下只公开清单。

### 签名

- 算法 Ed25519，用 `cryptography` 库。第一次启动生成钥匙对，公钥写进 `genesis` 记录。
- 私钥存进 macOS 钥匙串（`keyring` 库），不以明文文件存放。第一次成功记录后，提示用户导出一份带密码的备份。
- 签名对象 = 记录 ID 的 32 字节；签名存在 `records.signature`，导出时放进 `signatures/<id>.sig`。
- 钥匙丢失：只能新建安装和新的日志链；旧记录仍可验证。换钥匙的流程留到 v0.2。

### 两种时间证明

|  | 第三方签名时间证明 | 比特币时间锚定 |
| --- | --- | --- |
| 协议与默认服务 | RFC 3161，默认 [FreeTSA](https://freetsa.org/) | [OpenTimestamps](https://github.com/opentimestamps/opentimestamps-client)，官方默认日历服务器 |
| 状态 | 几秒内 `confirmed` | 先 `pending`，通常数小时内升级为 `confirmed`，时间不保证 |
| 信任前提 | 相信该机构的私钥和时钟 | 只依赖公开的比特币区块链 |
| 时间精度 | 秒 | 约数小时（区块时间） |
| 界面文字 | Third-party timestamp: verified | Bitcoin anchor: pending / confirmed |

**实现要求：**

- 统一接口 `TimestampProvider`：`submit(record_id, manifest_bytes)`、`upgrade(proof)`、`verify(record_id, proof)`。实现 `MockProvider`（测试用，结果确定）、`Rfc3161Provider`、`OtsProvider`。
- RFC 3161：用 [`rfc3161-client`](https://github.com/trailofbits/rfc3161-client)，版本不低于 1.0.6（更早版本有已公开的签名验证漏洞）。它不发网络请求，HTTP 用 `httpx`。把清单字节作为 data，**显式指定 SHA-256**，使摘要等于记录 ID；请求带 nonce 和 `certReq=true`。FreeTSA 的根证书和 TSA 证书内置在代码库里，不在运行时下载。
- OpenTimestamps：把清单字节当作文件来打时间戳，证明文件为 `<id>.json.ots`。启动时、运行中每小时、以及手动点击时检查升级。官方文档说明，完整验证比特币证明需要本地比特币节点（修剪节点即可）；没有节点时，从至少两个公开区块浏览器取区块头核对，并标明「经区块浏览器核对」。
- 网络失败进入重试队列（指数退避）。没有任何时间证明的记录显示「尚无时间证明」，不显示任何时间。
- 时间服务只收到哈希承诺和协议数据，收不到任何内容，但能看到请求的 IP 地址和时间。OpenTimestamps 文档提醒，短时间内连续提交的证明可能因时间相近被推断为同一人所为，报告的隐私说明里写明。

## 10. 验证

**白话：** 检查程序对每条记录逐项检查：内容的号码对不对、签名对不对、两种时间证明对不对、链条有没有断、引用的记录在不在。

| 编号 | 检查 | 通过条件 | 失败代码 |
| --- | --- | --- | --- |
| V1 | 内容 | 公开了内容的记录，正文和附件的 SHA-256 与载荷一致 | `CONTENT_MISMATCH` |
| V2 | 清单与载荷 | 清单的 SHA-256 = 记录 ID；载荷的 SHA-256 = 清单里的 `payload_sha256`；两者都是 JCS 规范形式；格式合法 | `MANIFEST_HASH_MISMATCH`、`PAYLOAD_HASH_MISMATCH`、`NON_CANONICAL`、`SCHEMA_INVALID` |
| V3 | 签名 | 用 genesis 里的公钥验证记录 ID 上的 Ed25519 签名 | `SIGNATURE_INVALID` |
| V4 | 第三方签名时间证明 | 签名有效，证书链到内置根证书，摘要 = 记录 ID | `TSA_INVALID`、`TSA_CHAIN_UNTRUSTED`、`TSA_IMPRINT_MISMATCH` |
| V5 | 比特币时间锚定 | 证明的起点是清单哈希；比特币证明经节点或区块浏览器核对 | `BTC_INVALID`；未确认为 `BTC_PENDING`，不算失败 |
| V6 | 日志链 | `seq` 从 0 连续；每条的 `prev` = 前一条的 ID | `LOG_GAP`、`LOG_PREV_MISMATCH` |
| V7 | 引用 | `relations`、`target`、`from`、`to` 指向的记录都在包里，且 `seq` 更小 | `REF_MISSING`、`REF_NOT_EARLIER` |
| V8 | 时间 | 两种时间始终分开报告，不合并成一个权威时间；界面如需一行摘要，写成「最早的已验证时间：X（来自哪一种证明）」；两种都没有就不给时间 | 无 |
| V9 | 来源标签 | 作者陈述和导入的声称日期不参与 V8 | 无 |

每条记录的结果只有四种：**通过**、**通过（比特币待确认）**、**警告**、**失败**（附失败代码）。两种情况给警告而不是失败：被引用记录的时间晚于引用它的记录（它的时间证明可能曾经失败后重试）；两种时间证明相差超过 24 小时。

验证逻辑只写一份，放在核心库 `provenance_core.verify`，应用和 `verify.py` 共用。`verify.py` 在构建时生成为单个文件，只依赖标准库、`cryptography`、`rfc3161-client`，`opentimestamps` 为可选。

### 手工验证（自动写进证据包的 VERIFY.md）

```bash
# 1. 内容、载荷、清单
sha256sum content/<id>/body.md     # 与 payloads/<id>.json 中的 content.body.sha256 比较
sha256sum payloads/<id>.json       # 与 manifests/<id>.json 中的 payload_sha256 比较
sha256sum manifests/<id>.json      # 结果应等于 <id>

# 2. 签名（需要 OpenSSL 3；macOS 自带的 LibreSSL 可能不支持，可用 Homebrew 安装 openssl@3）
echo -n <id> | xxd -r -p > id.bin
openssl pkeyutl -verify -pubin -inkey identity/public_key.pem -rawin -in id.bin -sigfile signatures/<id>.sig

# 3. 第三方签名时间证明
openssl ts -verify -data manifests/<id>.json -in proofs/<id>.tsr \
  -CAfile certs/freetsa-cacert.pem -untrusted certs/freetsa-tsa.crt

# 4. 比特币时间锚定（.ots 与清单放在同一目录）
ots verify manifests/<id>.json.ots
```

## 11. 界面

**白话：** 用户主要看一张演化图；点开任何一条记录，看到它的全部证据和后来追加的东西。界面文字用英文。

### 演化图（主画面）

- 从左到右按 `seq` 排列，上方标日期；按 9 种节点类型分行，只显示有记录的行。
- 箭头从旧记录指向新记录。三种关系线型不同：`revises` 实线，`derived_from` 虚线，`uses` 点线。后来用 `link` 补加的关系，旁边标补加日期；被撤回的关系显示为灰色并标撤回日期。

### 记录详情（侧栏）

按来源分区显示，标签固定：

1. **Verified record：** 内容或外部引用、记录 ID、签名状态、两种时间证明的状态和时间。
2. **Author statement：** 作者说明、导入的声称日期，每条都标「作者在某日声明」。

类型（9 选 1）、标题、正文（Markdown）或拖入文件、外部引用（代码：仓库地址 + 提交哈希，建议附打包文件；发表：DOI 或网址）、关系（选记录 + 3 选 1）、「为什么」（可选）、是否里程碑、导入选项（声称日期、L1 或 L2、参考链接）。提交按钮下方写明：提交后不能修改，只能追加。

### 时间线视图

按 `seq` 排列的列表，每行：两种时间证明的状态和时间、本地时间（灰色，标「unverified」）、类型、标题、关系、来源标签。

**白话：** 导出给别人的是一个压缩包。普通人打开网页报告看，懂技术的人运行检查程序或照着说明手工检查。

### 目录结构（格式标记 `rprov.bundle/1`）

```text
provenance-<名称>-<日期>.zip
├── report.html                 自包含报告，离线可开，可用浏览器打印成 PDF
├── bundle.json                 索引：格式版本、包含的记录、每条的公开程度、导出时的本地时间（未验证）
├── chain.json                  日志链：从 seq 0 到包内最高 seq 的全部记录 ID
├── VERIFY.md                   手工验证步骤
├── verify.py                   独立检查程序
├── identity/public_key.pem     签名公钥
├── manifests/<id>.json         清单（链上每一条都有，包括隐去的）
├── manifests/<id>.json.ots     比特币时间锚定证明
├── proofs/<id>.tsr             第三方签名时间证明
├── signatures/<id>.sig         签名
├── payloads/<id>.json          载荷（只限公开结构或全部公开的记录）
├── content/<id>/…              正文与附件（只限全部公开的记录）
└── certs/                      FreeTSA 根证书与 TSA 证书
```

### 每条记录的三种公开程度

| 公开程度 | 包含 | 读者能看到 |
| --- | --- | --- |
| 全部公开 | 清单、载荷、内容、证明、签名 | 全部 |
| 只公开结构 | 清单、载荷、证明、签名，不含内容 | 类型、标题、关系、作者说明、时间；看不到正文 |
| 只证明存在 | 清单、证明、签名 | 「第 n 条记录最迟在某时已存在」 |

导出前显示预览，逐条列出将被公开的内容。两个提示必须出现：「只公开结构」会公开正文和附件的哈希，别人已经拿到或容易猜到的内容（短句、已发表的段落、别人手里也有的文件），都可能被拿来对照哈希确认；`chain.json` 会显示本安装在包内最高 `seq` 之前共有多少条记录。

### report.html 的内容（按顺序）

1. 标题、作者标签（自我声明）、导出时的本地时间（未验证）。
2. **这份记录证明什么、不证明什么**：固定文字，取自第 2 节，用户不能删改。
3. 验证摘要：通过、比特币待确认、警告、失败各有多少条；注明这是导出时的结果，读者应自行验证。
4. 演化图（服务端生成的静态 SVG）。
5. 时间线表：两种时间证明分开成两列。
6. 每条公开记录的详情，按 Verified record / Author statement / Later additions 三个标签分区。
7. 方法说明：哈希、签名、两种时间证明、只追加规则，各用一段话讲清楚；隐私说明。
8. 如何自己验证：指向 `VERIFY.md` 和 `verify.py`。

CSS 全部内联，不加载任何外部字体、脚本或统计代码。打印时每页页脚写「本记录不证明作者身份或原创性」。

## 13. 技术架构

**白话：** 一个只在你 Mac 上运行的程序：浏览器界面、本地服务、核心库、本地存储。对外只把号码发给两个时间证明服务。

（示意图：本地架构，只有时间证明所需的哈希离开本机。图见在线文档第 13 节。）

核心库是唯一包含信任逻辑的地方；两个时间证明服务只收到哈希，收不到内容；证据包可以在任何一台电脑上独立验证。

### 技术栈

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 核心库 `provenance_core` | Python 3.12，纯函数：JCS、哈希、清单与载荷、签名、日志链、重放、验证、时间证明接口 | 信任逻辑只写一处，单元测试全覆盖；`verify.py` 由它生成 |
| 本地服务 | FastAPI、SQLAlchemy 2、SQLite | 单用户本地应用 |
| 签名 | `cryptography`（Ed25519）、`keyring`（macOS 钥匙串） | 见第 9 节 |
| 时间证明 | `rfc3161-client`（不低于 1.0.6）加 `httpx`；官方 `opentimestamps` 库 | 见第 9 节 |
| 后台任务 | 进程内调度：启动时一次，运行中每小时一次 | 不需要 Celery 或 Redis |
| 界面 | React、TypeScript、Vite；`@xyflow/react` 加 dagre；CodeMirror 6 编辑 Markdown | 常用、文档多 |
| 报告 | Jinja2 模板；演化图由服务端直接画成 SVG | 报告不依赖前端 |
| 测试 | pytest（核心、接口、篡改）；Playwright 一条端到端冒烟测试 | 见第 16 节 |
| 运行 | uv 管理依赖；`make dev` 开发；`make run` 在 `127.0.0.1:8765` 启动 | 一条命令能跑 |

### 代码库结构

```text

app/                    api/  db/  services/  jobs/  report/
web/                    React 界面
tools/build_verify.py   从核心库生成单文件 verify.py
fixtures/fsf_demo/      FSF 样例数据（虚构文本）

docs/                   PRD.md  DECISIONS.md
```

### 接口

| 方法与路径 | 用途 |
| --- | --- |
| `GET/POST /api/projects` | 项目列表、新建（改名只改本地显示名） |
| `POST /api/entries` | 新建 entry（multipart：类型、标题、正文、附件、外部引用、关系、作者说明、里程碑、导入选项） |
| `POST /api/links`、`/api/milestones`、`/api/statements`、`/api/retractions` | 追加其他种类的记录 |
| `GET /api/records/{id}`、`/content`、`/diff?against=` | 详情、内容、差异 |
| `GET /api/graph`、`GET /api/timeline` | 重放后的图和时间线 |
| `POST /api/anchors/refresh` | 手动检查时间证明 |

**写入规则：** 新建记录在一个数据库事务里完成，持有全局写锁：读最新记录 → 算出 `seq` 和 `prev` → 构建载荷和清单 → 签名 → 写入 → 提交。提交之后才申请时间证明，申请失败不影响记录本身。

## 14. 隐私与安全

**白话：** 内容不外泄；本地服务不能被恶意网页利用；钥匙不明文存放；电脑坏了数据也能恢复。

### 隐私

- **P1** 正文、附件、标题、说明永不离开本机；对外只发送时间证明所需的哈希承诺和协议数据。网络请求只允许出现在 `providers` 模块里；加一条测试扫描其他模块，禁止它们导入 `httpx` 或 `requests`。
- **P2** 数据目录 `~/.rprov/`，权限 0700。
- **P3** 不加任何遥测、统计或崩溃上报。
- **P4** 导出前显示预览，逐条列出将被公开的内容。

### 本地服务

- **S1** 只绑定 `127.0.0.1`，禁止绑定 `0.0.0.0`。
- **S2** 只接受 Host 为 `127.0.0.1:<端口>` 或 `localhost:<端口>` 的请求；校验 Origin；所有写操作需要启动时生成的随机会话令牌，令牌放在页面里，不放在网址里。这是为了防止恶意网页通过浏览器攻击本地服务。
- **S3** 上传文件单个上限 50 MB；清洗文件名防止路径穿越；按哈希存放；绝不执行上传的内容。Markdown 渲染时禁用原始 HTML，或用 DOMPurify 净化；报告同样适用。
- **S4** 恢复备份时解压要防路径穿越，并限制解压后的总大小。

### 钥匙与数据

- **S5** 私钥只存在 macOS 钥匙串里；导出的备份必须带密码。随机数一律用 `secrets` 模块。
- **S6** 依赖锁定版本（`uv.lock`、`package-lock.json`）；FreeTSA 证书内置，不在运行时下载。
- **S7** 数据丢失是本地应用最现实的风险。第一次成功记录后提示设置备份位置；提供一键完整备份（数据库、文件、钥匙备份）。

## 15. 威胁模型

**白话：** 记录之后的篡改都能被发现；记录之前的作假，和作者本人另起一套记录，防不住，只能在报告里写明。

| 威胁 | v0.1 的防御 | 剩下的风险 |
| --- | --- | --- |
| 事后改某条记录的内容 | 内容、载荷、清单层层哈希，再签名、留时间证明；改一个字节就验证失败 | 无 |
| 事后重新连线，改写演化图 | 关系写在被固定的载荷里；只追加规则；补加的关系带自己的日期 | 无；补加的关系一看就是后来加的 |
| 今天编出一串「早期记录」 | 这些记录的时间证明都是今天；本地时间只标「未验证」 | 无，前提是读者看已验证时间而不是声称日期 |
| 改电脑时钟倒签 | 时间只来自外部证明 | 无 |
| 预先记录很多种猜测，事后只公开猜中的 | 日志链显示「同期还有 N 条未公开记录」 | 作者可以另装一份应用另起一条链；报告写明完整度只限本链 |
| 删掉中间不利的记录 | 删数据库会造成断链；撤回本身是新记录 | 从没记进来的东西无法发现 |
| 拿别人的文字来记录，冒充作者 | 无法阻止；系统从不宣称作者身份 | 内在局限，报告写明 |
| 钥匙被偷 | 钥匙存在钥匙串里 | 偷钥匙的人能签新记录，但签不出过去的时间；签名只证明「同一把钥匙」 |
| 第三方时间机构签错时间或被攻破 | 比特币时间锚定作为独立的第二证明；两者相差超过 24 小时给警告 | 低 |
| 时间机构证书多年后过期 | 保存完整响应和证书链；比特币锚定作为长期证据 | 多年后可能需要额外处理 |
| 比特币确认前所有日历服务器消失 | 同时提交多个日历；第三方签名时间证明兜底 | 低 |
| 拿到记录 ID 反猜内容 | 载荷加盐 | 「只公开结构」时，别人已知或能猜到的内容可能被对照哈希确认，导出时有提示 |
| 恶意网页攻击本地服务 | 第 14 节 S1、S2 | 低 |
| 修改程序代码，写入任意记录 | 链和签名仍须自洽 | 本地软件防不住作者本人，只能证明「记录之后没有被改过」 |

## 16. 验收标准

**白话：** 下面 25 条自动测试全部通过，再完成最后 4 项人工检查，第一版才算完成。需要联网的测试（AC-09）默认跳过，在你 Mac 上手动跑。

| 编号 | 验收标准 | 测试类型 |
| --- | --- | --- |
| AC-01 | 固定输入（含中文、emoji、嵌套对象、乱序的键）规范化后与 RFC 8785 参考结果逐字节一致；测试向量文件里的记录 ID 永远不变 | 单元 |
| AC-02 | 载荷含浮点数时构建失败 | 单元 |

## 18. 哪些决定现在定死，哪些以后能换

**白话：** 一旦有真实记录被留下证明，有些东西再改就会让旧记录验证不了，这些必须现在定对；其余的以后随时能换。

### 现在必须定死

| 决定 | v0.1 选择 | 为什么改不了 |
| --- | --- | --- |
| 哈希算法 | SHA-256 | 旧的时间证明都绑定在它上面 |
| 规范化方式 | RFC 8785（JCS），禁止浮点数 | 换方式会改变所有记录 ID |
| 清单字段 | `schema`、`kind`、`installation`、`seq`、`prev`、`payload_sha256` | 记录 ID 由它决定 |
| 签名算法 | Ed25519，签名对象是记录 ID | 旧签名要一直能验证 |
| 记录种类 | 第 8 节的 6 种 | 重放规则依赖它 |
| 加盐位置 | 载荷里的 32 字节随机数 | 已留证明的记录无法补盐 |
| 正文规范化 | UTF-8、LF | 改了以后旧正文的哈希对不上 |
| 证据包格式 | `rprov.bundle/1` | 已发出去的包必须一直能验证 |

留了退路：清单和证据包都带格式版本号。以后可以新增 v2 与 v1 并存，但检查程序必须永远支持旧版本。节点类型和关系种类允许以后新增；旧的检查程序遇到新种类照常验证。

### 以后可以换

| 决定 | v0.1 选择 | 什么时候可能换 |
| --- | --- | --- |
| 本地还是同步 | 只在本地 | 需要多台设备或协作时，改为端到端加密同步 |
| 技术栈 | FastAPI、React | 任何时候 |
| 数据库 | SQLite | 多用户时换 Postgres |
| 第三方时间机构 | FreeTSA，可配置 | 需要更高可信度时增加或改用商业机构 |
| 图的画法 | React Flow、dagre | 任何时候 |
| 报告格式 | HTML | 加 PDF |
| 界面语言 | 英文 | 加中文 |
| 证据标签的措辞 | 第 2 节的写法 | 同学试用之后调整 |

### 为以后预留，但不实现

| 以后的方向 | 现在已经具备或预留的 |
| --- | --- |
| 第二版 AI 分析 | `statement` 记录的 `source` 字段（`ai`）和 `based_on`；第 4 节的 5 条规则 |
| 自动记录（git、笔记软件） | 追加接口已有；以后加命令行工具 |
| 贡献分析、多人合作 | 签名身份；带类型的关系；以后加「钥匙与真实身份绑定」，例如 ORCID |
| 论文审计 | `claim` 节点类型；`uses` 关系；记录 ID 可作稳定引用 |
| 公开透明日志 | 日志链结构已具备 |

## 附录：FSF 测试方案与同学试用

### FSF 测试步骤

1. 把 FSF 以前的材料收集起来，按日期排好：笔记、公式、代码、实验结果、图、预印本。
2. 如果预印本还没有在 Zenodo 或 OSF 存档，先存档拿到 DOI。它会是最强的第三方参考。
3. 逐条导入：如实填写声称日期；有第三方记录的（DOI、发给别人的邮件、网页存档）标 L2，其余标 L1。
4. 从导入那天起，每次有实质进展就正式记录一条，并挑出里程碑。
5. 两周后，打开「只看里程碑」，回答第 6 节的 FSF 检验：只看这张图，是不是比「GitHub + 文件夹 + 直接问 AI」明显清楚？把答案和理由写下来。
6. 导出一份「只公开结构」的证据包，作为申请材料的附件。

### 同学试用（3–5 人，一周）

- **开始前：** 请对方选一个自己正在做、会持续几个月的研究。
- **问一句话：** 「如果你在做一个持续几个月的研究，你愿不愿意在几个关键节点顺手留下这条记录？为什么？」
- **看实际行为：** 一周内他们实际记了几条？有没有标里程碑？有没有导出过？
- **记下卡住的地方：** 安装、记第一条、理解两种时间证明、看懂报告。
